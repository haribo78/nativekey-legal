# NativeKey Managed AI — Google Play Data Safety checklist

Last reviewed: 2026-11-15

This checklist is tied to the current NativeKey implementation and must be re-checked before every production release that changes data flows.

Official references:
- https://support.google.com/googleplay/android-developer/answer/10787469
- https://support.google.com/googleplay/android-developer/answer/10144311

## Release rule

Current public 1.0.1 does not include the Managed AI transport path. Before Managed AI is promoted to Production, update the Play Console Data safety form and published Privacy Policy so both describe the same off-device data flows.

Google Play defines "collect" broadly as transmitting user data off device, including ephemeral processing and pseudonymous data. NativeKey AI therefore requires Data Safety declarations even though AI runs only after an explicit user action.

## Recommended Managed AI declarations

### Other user-generated content

- Collected: YES when the user invokes NativeKey AI.
- Required or optional: OPTIONAL at app level; NativeKey can be used without Managed AI.
- Purpose: App functionality.
- Encryption in transit: YES (HTTPS).
- Advertising/marketing: NO.
- Personalization: NO, unless product behavior later changes.
- Retention by NativeKey backend: no long-term typing history; a completed response can exist briefly in the idempotency cache, then expires/purges.
- Third-party inference: the request is sent from the NativeKey backend to the configured inference provider.

### Device or other IDs

Current value: random app installation UUID generated by NativeKey. It is not Android ID, advertising ID, IMEI, serial, phone number, or email.

- Collected: YES for Managed AI.
- Required or optional: OPTIONAL at app level; required to use Managed AI.
- Purposes: App functionality; Fraud prevention, security and compliance; quota/abuse prevention.
- Analytics: select YES only if the retained installation-linked usage records are used for product/usage analysis, not merely request enforcement.

### App interactions

Examples currently retained or derivable: AI request count, AI mode, source/target language metadata, app version/version code.

- Collected: YES for Managed AI technical records.
- Required or optional: OPTIONAL at app level.
- Purposes: App functionality; Analytics; Fraud prevention, security and compliance where applicable.
- Never include input text or output text in this category as a workaround; content must be declared under its actual content type.

### Diagnostics

Examples: latency and normalized error/status metadata.

- Collected: YES when Managed AI is used.
- Required or optional: OPTIONAL at app level.
- Purposes: Analytics and App functionality.

### Messages

NativeKey does not read an email mailbox, SMS database, or chat database. It only processes text that the user explicitly asks the keyboard to transform or translate.

Because NativeKey includes Incoming/Reply communication flows, review the final Play Console wording conservatively:
- Other in-app messages: declare if the production positioning/use case explicitly treats submitted content as chat/message content.
- Emails and SMS/MMS: declare if the released product or store listing explicitly supports processing those message categories as such, rather than generic user-provided text.

Do not under-declare merely because the text reached NativeKey through a keyboard or clipboard action.

## Sharing

The Data Safety form distinguishes collection from "sharing." Transfers to a qualifying service provider processing data on the developer's behalf can fall under a sharing exception, and some explicit user-initiated transfers can also fall under an exception.

For NativeKey AI:
- Always declare the underlying data as collected when it is transmitted off device.
- Do not mark the inference-provider transfer as "not shared" solely by assumption.
- Before production submission, confirm the applicable processor/service-provider terms for the configured AI provider and use the Play definition in force at submission time.
- If uncertain, use the conservative declaration.

## Security / privacy statements that are currently supportable

- Data in transit is protected with HTTPS.
- Normal typing does not call Managed AI.
- AI transmission starts only after an explicit AI action.
- Protected fields block AI where designed.
- NativeKey application logs reject input_text, output_text, prompt, clipboard, API key, authorization, installation-token, and Google Play purchase-token fields.
- Backend stores technical metadata for quota, reliability, security and accounting.
- A completed AI response may be cached temporarily for idempotency; current default TTL is 120 seconds.
- NativeKey does not require a NativeKey user account for Managed AI.
- NativeKey does not use normal typing content for advertising.

## Deletion mechanism

The Privacy Policy provides nativekey.support@gmail.com for data/deletion requests.

Because Managed AI uses a random installation identity rather than a NativeKey account, any future deletion workflow must provide a practical way to identify the installation records that should be deleted. Do not promise account-based deletion until an account system exists.

## NativeKey AI Pro subscription — Production form impact

The v9 Internal Testing implementation sends a Google Play purchase token to the NativeKey backend for server-side verification and acknowledgement. The backend retains a SHA-256 token hash plus subscription-entitlement metadata, but not the raw token.

Before any Production release containing NativeKey AI Pro, update the Play Console Data safety form.

### Financial info → Purchase history

Recommended declaration for the implemented subscription path:

- Collected: YES.
- Required or optional: OPTIONAL at app level; required only when the user chooses NativeKey AI Pro.
- Purposes: App functionality; Fraud prevention, security and compliance.
- User payment info: NO, provided NativeKey continues not to access card/bank/payment-account details handled directly by Google Play.

Google’s current Data Safety guidance distinguishes payment information handled directly by Google Play from other financial information the app receives, including purchase history. NativeKey receives and retains subscription-state/entitlement information, so do not rely on the payment-processor exception to omit Purchase history.

Also re-check:
- Device or other IDs / random installation association;
- App interactions;
- server-side entitlement records;
- whether any provider transfer qualifies for a Play “sharing” exception at submission time.

Do not publish the subscription build with the old Data Safety answers.
